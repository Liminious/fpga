# PCB 故障诊断：采集端、悟净 CPU 与模型对接表

> 日期：2026-10-11。接口草案 v0.1，基于单 DDS、单 ADC 两次顺序测量原型。
> **当前只有随机权重联合模型和 ONNX 验证，没有训练完成的诊断模型。**
> 本表区分已实现的仿真接口与建议新增的实板字段，最终张量规格、精度和输出类别要在 ICraft 3.36.1 与 NPU 验证后冻结。

## 1. 最重要的结论

- 采集端向悟净 CPU 交付：**每次测量一份 CSV，加对应 JSON 记录与测试动作。**
- 正常设计由上位机/CPU提供：正常网表、标称参数、容差和节点/测点映射。
- 悟净 CPU 进行检查、重采样、归一化和图编码，生成数值张量。
- NPU 接收：**按编译模型约定的形状、顺序和数据类型组织的输入缓冲区**，不是直接打开 CSV、JSON 或网表。
- `.npz` 是当前电脑端保存多组数组的中间文件，不是 NPU 通用加载格式。
- 模型编译产物由训练/部署负责人交付；与每次测试数据分开保存。

```text
正常网表/参数/测点定义 ────────────────┐
                                    ↓
7020采集 → CSV + JSON → 悟净CPU预处理 → NPU输入缓冲区
                                    ↓
                           编译后的模型进行推理
                                    ↓
                      CPU还原元件/节点名称，管理候选
```

## 2. 队友分工与交付

| 对接方 | 交付内容 | 格式 | 谁使用 | 当前状态 |
|---|---|---|---|---|
| 电路/设计负责人 | 正常设计网表 | 支持范围内的SPICE `.cir`，其他格式需适配 | CPU解析器 | 已有简单R/C样例，不是通用PCB解析器 |
| 电路/CPU负责人 | 元件、节点、标称值、容差 | `circuit_graph.json` | CPU预处理 | 仿真样例已有显式图 |
| 机械/CPU负责人 | 测点ID到电气节点、焊盘坐标的映射 | JSON/双方约定结构 | 测试规划和机械执行 | 实板映射尚未确认 |
| CPU测试规划器 | 激励节点对、测量节点对、激励与采样请求 | `test_action.json`或同字段TCP消息 | 7020/执行器 | 样例已有，硬件协议需实现 |
| 7020采集负责人 | 单通道电压序列及相对时间 | 每次一个 `wave.csv` | CPU | 已有仿真样例；实测待提供 |
| 7020/执行器负责人 | 实际执行结果、质量、时序和配置 | `measurement_record.json`及扩展元数据 | CPU | 基础仿真记录已有，实板扩展待实现 |
| CPU负责人 | 按顺序组织多次测试 | `measurement_history.json` | CPU预处理 | 样例已有 |
| AI负责人 | 预处理代码、输入规范、映射和版本 | Python/文档/JSON | CPU集成 | 原型脚本已有，板端移植待实现 |
| AI/部署负责人 | 编译产物、运行示例、验证向量 | 以ICraft目标运行时要求为准 | 悟净NPU调用程序 | 尚未完成ICraft/板端验证 |
| CPU负责人 | 推理结果解释、参数拟合、下一项测试 | 接口待正式定义 | 网页及设备控制 | 尚未实现完整闭环 |

CSV是先打通接口的文件格式。TCP实时传输可以使用JSON元数据加二进制样本，并由CPU存成同样的文件。该网络协议尚未实现，不能把一个采样点发一条JSON作为已确定设计。

## 3. 采集端需要交付什么

### 每次测试必须能明确的信息

| 字段/信息 | 类型/单位 | 提供方 | 要求 |
|---|---|---|---|
| circuit_id及设计版本 | 字符串 | CPU下发，采集端回传 | 绑定同一正常设计；正式系统需增加版本/哈希 |
| episode_id | 字符串 | CPU | 同一块待测板、同一诊断过程 |
| action_id | 字符串 | CPU下发 | 对应请求的测试动作 |
| record_id | 字符串 | CPU/采集端约定 | 本次执行的唯一ID，重试生成新ID |
| sequence_index | 整数 | CPU | 执行顺序，不能靠文件名推断 |
| 激励正/负节点 | 字符串节点ID | CPU下发 | 必须存在于正常设计 |
| 测量正/负节点 | 字符串节点ID | CPU下发 | 说明ADC电压的方向 |
| 激励类型与实际执行设置 | 数值，V/Hz/s等 | 采集端回传 | 设置值与实际测得值分开，不把设置值冒充实测 |
| time_reference | 字符串 | 双方约定 | 明确零时刻是什么事件 |
| 相对时间或样本索引+dt | 秒/整数 | 7020本地 | 不能用TCP收包时间代替采样时间 |
| sample_count | 整数 | 采集端 | 必须与实际样本数量一致 |
| 电压 | 数值，V | 采集/CPU约定 | 此文件接口统一交付已换算的V |
| status | 字符串 | 采集端 | complete/failed等，失败不能当正常波形 |
| source | 字符串 | 采集端 | 实板hardware，仿真simulation |

节点和动作由CPU/设计侧确定，不要求FPGA自己解析网表。采集端可只回传动作ID，CPU必须保存其与节点、配置的不可混淆对应关系。

### 实板建议新增且需要联合实现的元数据

以下不是当前仿真脚本已经验证的能力：

- ADC型号、量程、码值换算方法、增益/零点校准版本。
- 丢样/溢出、饱和、采集超时与触发是否有效。
- 时钟/采样配置和已知触发到模拟输出的延迟。
- 接触状态：有效、无效或未知；未知不能伪装有效。
- 激励输出阻抗、限流状态、是否有独立实际激励监测。
- 放电/复位方法、实际等待时间和激励前基线检查结果。
- 两遍测试开始时间与重试记录，用于检查重复性和追溯。

CPU必须检查这些质量信息后才选择可用测量。当前输入脚本主要检查数值、节点、形状和顺序，还没有实现全部实板质量判断。

如果保留ADC原始整数码，单独归档并提供明确校准转换；不要将整数码直接写进名为voltage_V的列。未知参数写null并报告缺项，不猜测数值。

## 4. 单ADC顺序测量的约定

| 顺序 | 激励 | ADC0测量 | 记录 |
|---|---|---|---|
| 1 | VIN对0，同一套允许的激励 | VIN对0 | test_01_vin |
| 2 | 恢复初始状态后重复激励VIN对0 | OUT对0 | test_02_out |

- 两次分别采集，不是同步双通道。
- 第一遍VIN只能作为重复性前提下的输入参考，不能证明第二遍实际VIN完全一样。
- 撤除激励后恢复状态，移探针并确认到位，再执行下一次测试。
- 电容放电时间按实际电路与故障状态确定，不统一硬编码10ms。
- 仿真样例的地为节点0，实板接地、回流和供电方案需要队友确认。
- 第一版相位诊断没有经过验证；先做可重复的阶跃/幅值测量。

## 5. 文件组织与CSV格式

建议一组诊断过程组织为：

```text
episode_E001/
├─ normal.cir
├─ circuit_graph.json
├─ measurement_history.json
├─ test_01_vin/
│  ├─ test_action.json
│  ├─ measurement_record.json
│  └─ wave.csv
└─ test_02_out/
   ├─ test_action.json
   ├─ measurement_record.json
   └─ wave.csv
```

文件名与字段沿用已生成的顺序测量样例，以减少改动；新增质量字段应由CPU预处理验证。

CSV表头必须为：

```csv
time_from_trigger_s,voltage_V
```

- 时间以秒计，电压以伏计。负时间可表示激励事件之前的预采样。
- 不使用毫秒值冒充秒、不使用mV冒充V。
- 时间必须严格递增；样本数量与JSON一致。
- 不得包含NaN或Infinity；缺失数据按无效测量处理，不补成真实0V。
- 默认保存原始采样分辨率，CPU统一重采样；采集端不需要直接输出128点。
- 当前理想例子每遍801点、10μs间隔、相对触发−1ms到+7ms，这是样例参数，不是已确认的实板采样能力。

两次test_action都使用channel_id=ADC0；positive_node分别是vin和out，negative_node为0。
当前仿真time_reference为commanded_stimulus_rising_edge，即指令定义的激励上升沿。实板必须明确对应的FPGA事件，并记录/校准到实际模拟输出的延迟，不能把它自动视为无误差的真实边沿。

## 6. CPU预处理后模型接收的类型

当前模型有7个运行时输入，接口是**有名称的float32张量**：

| 名称 | 形状 | 信息 | 生成方 |
|---|---|---|---|
| X | [1,16,8] | 最多8元件+8电气节点的属性 | CPU解析与编码 |
| A | [1,16,16] | 电路连接、自身连接和行归一化 | CPU图编码 |
| M | [1,16,1] | 有效顶点，屏蔽补齐位置 | CPU |
| P | [1,2,2,16] | 2次测试，每次激励节点对+测量节点对 | CPU动作映射 |
| W | [1,2,1,128] | 2次测试，各1通道，各128点 | CPU波形预处理 |
| S | [1,2,10] | 激励设置与采样时间信息 | CPU |
| H | [1,2] | 哪次测量已取得且被纳入输入 | CPU |

名称和输入列表顺序当前为X,A,M,P,W,S,H，但集成应按编译模型输入签名核对，不只依赖数组排列猜测。

当前缩放：W的V值除3.3；S电压除3.3，时间除1ms；元件值以固定参考值做log10缩放。完整字段含义参见LOCAL_CODEX_HANDOFF.md及prepare_sequential_inputs.py。

未测第二次：H=[1,0]，对应位置补零；两次都有有效结果：H=[1,1]。不能将一条采集失败记录标成已有效完成。

npz中保存这些数组，方便电脑检查；板端可在内存里直接构建，无需先写npz再读取。ICraft量化后模型输入是否需要其他精度、布局及转换，必须读取编译产物的接口约定，不擅自把float32强转成int8。

这个原型只支持两次指定测试，并不等于最终多轮历史模型已完成。新增测试动作/容量必须更新训练、预处理和部署接口。

## 7. 模型负责人交付清单

正式模型应交付：

1. 经过验证的ONNX和ICraft目标编译产物，注明CLI、运行时与目标版本。
2. 输入签名：名称、顺序、shape、dtype、布局、单位、缩放、掩码规则。
3. 一致的CPU预处理实现，注明版本并保留对应训练预处理。
4. 元件/节点索引到实际ID的映射规则，不能把R1等名称当训练类别。
5. 输出含义、阈值/校准、支持范围和证据不足处理。
6. 一组输入与预期输出，供板端对照；量化精度及延迟报告。
7. CPU调用示例及错误处理，确认实际执行NPU。

当前已有joint_smoke.onnx、随机权重与电脑端验证向量，但尚未完成ICraft/板端验证。
当前输出[1,8,3]只有3个演示分数，不是故障概率，不能做实际故障报告。
未来故障输出、节点对短路候选、CPU参数拟合和多轮测试规划需要另行定义与验证。

## 8. 训练标签必须与运行输入分离

训练时可以另存label.json，记录故障元件/类型/真实参数，作为监督答案。
现场推理不应要求知道这些答案，也不读取label.json。
正常设计不能替换成已经注入故障的真实网表作为输入。
示例仿真目前没有ADC、触点、激励漂移模型，不能当作已经验证的实板精度或训练泛化。

## 9. 队友现在可以完成的最小对接验收

- 提供一组真实的两遍采集，各一份CSV及对应动作/记录。
- 明确激励/测量节点对、固定参考节点、单位、时序和状态。
- 核对两遍同一电路/诊断过程、同一设定、初始状态可重复。
- CPU能识别数据有效性、产生固定输入，且标签未进入输入。
- 在ICraft/板端部署完成后，用固定验证向量检查接口，再接实际采集。

不以“收到CSV”“网络已连通”或“CPU能跑ONNX”作为NPU部署完成证据。
